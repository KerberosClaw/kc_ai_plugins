# 發現契約

階段 1 的產出規格。一條發現要回答得出下面七欄才算數，答不出來的退回去補，不要帶著空欄進報告。

## 編號

| 前綴 | 意思 | 怎麼找到的 |
|---|---|---|
| `GAP-##` | 需求寫了，程式沒做 | 從需求往程式碼找 |
| `UND-##` | 程式做了，需求沒寫 🔴 | 從程式碼往需求找 |
| `MIS-##` | 兩邊都有，但講的不是同一件事 | 兩邊擺在一起讀 |
| `EC-##` | 邊界與前提 | 沿八個面向挖 |

同一輪內連號。下一輪開新號，不回收舊號，這樣報告之間引用才不會錯位。

## 七欄

| 欄 | 寫什麼 |
|---|---|
| 編號 | 上表的前綴加流水號 |
| 系統實際怎麼做 | 一句話講清楚。例：「建立專案前會檢查分類表至少有一筆，沒有就回 400」 |
| 出處 | 檔案加行號、schema 欄位、文件段落，或實跑紀錄。後面加註證據狀態（見下） |
| 需求怎麼說 | 引需求文件原文並註明段落。完全沒提就寫「需求未提及」，這一欄空著的 `UND` 就是還沒查完 |
| 誰會踩到 | 哪個角色、在什麼前提下、做了什麼操作。牽涉數值（上限、逾時、次數）一定附出處；找不到出處就寫「數值不明」並列成待問 |
| 優先序 | P0 到 P3，後面一句理由，至少講到「誰受影響、多常遇到、踩到了自己看不看得出來」 |
| 下一步 | 會轉成哪幾條 `TC-##`；還有哪些不確定、要問誰；什麼情況出現就可以結案 |

### 證據狀態

「出處」欄後面一定要標以下四種之一：

- `已查證`：原文讀到了
- `推論`：從讀到的東西推出來的，把推的過程寫出來
- `待驗證`：要實際跑過才知道
- `無法查證`：材料不夠，寫明缺什麼

## 三方對照的實際做法

### `GAP`：拿著需求去找程式

需求裡每一句可驗證的話，都問一次「程式碼哪裡實作了它」。找不到就開一條 `GAP`。

⚠️ 找不到可能只是找錯地方，所以預設標 `推論`，並寫下找過哪幾個檔案。

### `UND`：拿著程式去找需求 🔴

反方向走。先把程式碼裡**所有會讓使用者走不下去的地方**撈出來，再一條條回頭找需求有沒有講過。

特別要撈這幾種：

- 權限與角色判斷
- 「必須先有某某」的前置檢查
- 防重複、只能做一次
- 必填、格式、長度限制
- 狀態轉換的限制（什麼狀態不能做什麼）
- 寫死在程式或種子資料裡的預設值與領域假設：欄位名稱、選項清單、分類字典

需求裡找不到對應的，就是一條 `UND`。

🔴 **`UND` 是問題，不是缺陷。** 它代表「這件事沒有人拍板過」。處理方式是寫成問句丟回給人：「系統現在要求 X，這是你要的嗎？」合理的就補進需求或手冊，不合理的才升級成缺陷。

### `MIS`：兩邊都講了，但意思不一樣

最常見的三種錯位：

- **什麼叫成功**：後端回 200 但事情沒成；或前端把失敗的回應當成功顯示
- **影響多大**：畫面看起來只改這一筆，實際上改了整個資料庫
- **什麼時候完成**：一邊以為當下就完成，另一邊其實是丟進佇列慢慢跑

⚠️ 單看一邊永遠找不到這類問題，因為每一邊自己都說得通。

## 八個挖掘面向

`EC` 沿以下八個面向挖。每個面向挑兩三條最可能出事的就夠了，挖出一百條平均用力的邊界等於沒挖。

| 面向 | 問什麼 |
|---|---|
| 資料從哪裡來 | 🔴 **全新環境什麼都沒有的時候**走得通嗎？字典、分類、預設設定是不是空的？第一筆資料由誰、在哪裡建？ |
| 填進去的值 | 空的、極大極小、剛好超過上限、格式不對、單位混用、特殊字元、多送了欄位 |
| 時間與先後 | 時區、跨日、過期、未來時間、步驟順序顛倒、同一件事送兩次、兩個人同時做 |
| 狀態 | 不該允許的轉換、做到一半中斷、只能做一次的動作做第二次 |
| 誰在操作 | 不同角色與權限、不同瀏覽器與裝置、不同語系 |
| 系統外部 | 配額、容量、磁碟、外部服務掛掉、逾時 |
| 畫面上的字 | 提到的東西存在嗎、用的是使用者的語言嗎、擋下來時說得出原因嗎（細節見 `SKILL.md` 1b） |
| 疊在一起 | 前面幾項單獨都沒事，同時發生才出事的情況 |

🔴 **第一個面向最常被漏掉。** 開發和測試環境早就塞滿資料，「分類表是空的」「第一筆還沒建」這種問題在那裡永遠不會發生，一到新客戶的環境就整條路被擋住。每一輪都要明確回答一次：什麼都沒有的時候，這條路走得通嗎？
