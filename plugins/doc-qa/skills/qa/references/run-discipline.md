# 執行紀律

階段 3 的規格。**跑之前整份讀完。**

## 開跑前的五道關卡

一道沒過就不准跑，改標 `NOT RUN` 並寫明卡在哪。

| 關卡 | 要確認什麼 |
|---|---|
| 這是什麼環境 | 開發、測試、預發布或正式。**正式環境一律唯讀，沒有例外** |
| 資料能不能丟 | 這輪會不會寫入。會的話，這份資料弄髒了有沒有關係、重建得回來嗎 |
| 帳號拿到了嗎 | 矩陣裡每個角色都要有對應帳號。缺的角色整欄標 `NOT RUN`，不要用管理員帳號代跑然後當作驗過了 |
| 前提重建得出來嗎 | 見下一節 |
| **證據通道通不通** | 見下下節 |

### 🔴 先確認證據留得下來，再開始跑

**第一個動作是採一次證據，不是跑第一條案例。** 截一張圖、撈一次網路紀錄、取一次無障礙樹，確認三個通道都拿得到東西。

通道壞掉時，它不會讓案例失敗，只會讓**證據悄悄消失**——跑完才發現整輪一張圖都沒有，而那時候環境已經被寫過了，重跑的成本是整輪。

通不過就當場決定並寫進報告：降級用其他訊號判定（判定通常不受影響，因為判定本來就不靠圖），或停下來修工具。**不准默默跑完再說。**

### 不可逆的動作要事前點出來

「資料能不能丟」那一關問的是整個環境，但環境可丟不代表每個動作都可以重來。有些動作**在可拋棄環境裡一樣回不去**：永久刪除、一次性顯示的憑證、只能決定一次的選擇、單調遞增的版本號。

開跑前把這類動作列出來。跑到的時候要嘛先問、要嘛明確記成「已知並接受」，**不要跑完才在寫入清單裡發現它**。

### 前提重建不出來就誠實標記

矩陣的橫軸是前提組合，但有些前提在現成環境裡重建不出來。最常見的是「全新環境什麼都沒有」：環境早就有資料了，沒有辦法退回空白狀態。

**這種情況標 `NOT RUN` 加上原因，不要用「看起來應該沒問題」代替。** 一條沒跑過的案例標成沒跑，比標成通過有價值得多。

如果環境重建得起來（有初始化腳本、容器可以重開、資料庫可以還原），就在報告裡寫明重建方式，那是可重現性的一部分。

## 🔴 不准改動目標系統

- **預設唯讀。** 只看、只點不會寫入的東西
- 要寫入之前先過上面第二道關卡，並且**把每一個寫入動作記下來**：什麼時間、哪支端點、寫了什麼、留下什麼資料
- 報告必須有一節列出本輪所有寫入動作，方便事後清理
- **不准為了讓測試過就去改資料、改設定、改程式碼**
- 不准動正式環境的任何寫入路徑，包含看起來無害的「儲存偏好設定」

## 五種結果狀態

二元的通過與失敗不夠用，這五態缺一不可。

| 狀態 | 定義 | 判準 |
|---|---|---|
| `PASS` | 行為符合預期，而且使用者知道發生了什麼 | 兩個條件都要成立 |
| `FAIL` | 行為不符預期 | 預期依 `依需求` 或 `推定` 那條 |
| `UNCLEAR` | 行為正確，但使用者無從得知為什麼 | 見下 |
| `BLOCKED` | 走不到這一步，被前面某個關卡擋住 | **這本身是一條發現** |
| `NOT RUN` | 沒跑 | 缺環境、缺資料、缺帳號、前提重建不出來 |

### 🔴 `UNCLEAR` 是本 skill 的重點格

系統正確地擋住了某個操作，但使用者看到的是一個看不懂的失敗、一個沒有說明的空畫面、或什麼都沒發生。

**行為是對的，體驗是壞的。** 記成 `PASS` 會讓卡關的主因整個消失，記成 `FAIL` 又會誤導人去改一段本來就正確的邏輯。

判準：走到這一步的人，**光看畫面**知不知道

1. 剛剛發生了什麼
2. 為什麼會這樣
3. 接下來該做什麼

三個問題有任何一個答不出來，就是 `UNCLEAR`。

`BLOCKED` 和 `NOT RUN` 要分清楚：**`BLOCKED` 是系統擋的，那是發現；`NOT RUN` 是我們沒跑，那是證據缺口。**

## 怎麼判：看樹不看圖

🔴 **判定用 `browser_snapshot` 的無障礙樹，不要用截圖判。** 截圖是給人看的證據，不是判定的依據。畫面上看起來對，不代表底下狀態對。

### 三個訊號一定要一起看

只看畫面會漏掉一整類問題，尤其是「回成功但其實沒成」。

| 訊號 | 工具 | 抓什麼 |
|---|---|---|
| 畫面與結構 | `browser_snapshot` | 元素在不在、狀態對不對、文字寫什麼 |
| 網路 | `browser_network_requests` | **狀態碼與回應內容是否一致**、有沒有預期外的請求、有沒有靜默失敗的請求 |
| 主控台 | `browser_console_messages` | 未捕捉的錯誤、警告、被吞掉的例外 |

🔴 **「上傳失敗卻回成功狀態碼」這類問題只有比對網路訊號才抓得到。** 畫面顯示成功、使用者以為成功，要打開實際的回應內容才看得出裡面寫著失敗。每條牽涉到送出資料的案例，都要把對應的請求與回應撈出來看，不能只看畫面跳到哪。

### 等待

用 `browser_wait_for` 等明確的條件，不要用固定秒數硬等。等不到就是等不到，那可能就是一條發現（非同步完成但介面沒有回饋）。

## 截圖規則

同一趟走完全程，**兩種素材一起採**。走都走了，只截失敗的地方等於丟掉一半產出。

| 類別 | 什麼時候截 | 給誰用 |
|---|---|---|
| `defect` | `FAIL`、`UNCLEAR`、`BLOCKED` 發生的當下 | 缺陷報告的證據 |
| `manual` | 成功路徑的每一個關鍵步驟 | 之後交給 `project-docs` 寫手冊 |

### 命名

```
<輪次>/<類別>/<案例編號>-<步驟序>-<簡述>.png

20260918-r1/defect/TC-07-03-上傳後回成功但清單沒出現.png
20260918-r1/manual/TC-02-01-進入建立頁.png
```

輪次用日期加流水，**第二輪不要覆蓋第一輪**。同一條案例在不同前提下跑，前提要寫進簡述。

### 截圖不是證據的全部

每張圖旁邊要有一行文字說明「這張圖證明了什麼」。單獨一張圖不構成證據，圖加上當下的網路與主控台訊號才算。

## 矩陣怎麼跑

橫軸是前提組合，縱軸是測試案例。**不要跑滿笛卡爾積**，每條案例只跑它真正適用的前提。

```
                      全新環境   已有資料   非管理員   第二次執行
TC-01 上傳單張圖       BLOCKED     PASS      FAIL       UNCLEAR
TC-02 批次匯入         NOT RUN     PASS      FAIL       BLOCKED
```

- 空白格代表「這條案例在這個前提下沒有意義」，要在報告裡說明為什麼不適用
- `NOT RUN` 代表「有意義但沒跑」，要寫原因
- **兩者不可混用。** 沒意義和沒跑是兩件事

## 跑完要留下什麼

1. 矩陣本體
2. 每個非 `PASS` 格子的證據包：截圖、網路訊號、主控台訊號、當下的無障礙樹片段
3. 本輪所有寫入動作的清單
4. 環境與版本紀錄：哪個環境、哪個版本或提交、什麼時間跑的、用哪些帳號
5. `manual` 類截圖的完整成功路徑
