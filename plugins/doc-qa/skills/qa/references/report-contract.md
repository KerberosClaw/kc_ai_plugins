# 報告契約

階段 4 的規格。**出貨前跑完文末十條自檢。**

報告格式跟著分級走（分級見 `SKILL.md`「先分級」）：

| 級別 | 報告 |
|---|---|
| 免測級 | 一句話：「依分級免測：本次只改文件（列出檔案）。」不造矩陣、不跑自檢，也不寫成 QA 通過 |
| 回歸級、畫面級 | 精簡格式（見下方「精簡格式」與 `templates/qa-report-lite.md`），十條自檢照跑，用不上的項目寫不適用 |
| 完整級 | 完整格式（見下方「報告結構」與 `templates/qa-report.md`） |

## 整體狀態與它的證據限定詞

報告摘要的開頭先寫分級，緊接著就是整體狀態與出口判定。判整體狀態時先看分級，再依 ui-driver 確認適用性，然後按下表由上往下命中第一列；有矩陣時，狀態必須能由矩陣決定：

| 矩陣長什麼樣 | 整體狀態 |
|---|---|
| 分級為免測級，附改動清單 | `依分級免測` |
| 已查證產品在核准範圍內本來就沒有適用 UI，附範圍與實作依據（只是這次改動沒碰到畫面，是回歸級，不屬於這一列） | `UI QA 不適用` |
| 尚不能確認不適用，且一格都沒跑（含適用性待確認、沒有環境或還沒開始） | `尚未實跑` |
| 有些格子跑了，有些是 `NOT RUN` | `部分執行` |
| 適用格子都有執行紀錄，仍有未結案 `FAIL`／`UNCLEAR`，或任一 `BLOCKED` | `已執行，有未結案缺陷或阻塞` |
| 適用格子都有執行紀錄，沒有未結案缺陷或阻塞 | `已執行，本輪範圍內無未結案缺陷或阻塞` |

`BLOCKED` 代表案例目標沒驗到，必須連到上游阻塞／發現與影響範圍；整輪只有 `BLOCKED` 也屬「有未結案缺陷或阻塞」，不能算全部通過。修好阻塞後補跑，保留前輪紀錄。若案例本來就是驗證正確阻擋，結果依預期判 `PASS`／`UNCLEAR`，不因看見阻擋就記 `BLOCKED`。

回歸級與畫面級照同一張表判，「格子」就是該級排定的案例與回歸腳本的題目。限定詞一定要寫出分級與沒涵蓋的部分，例如「回歸級：依分級未開瀏覽器，畫面沒有實測」。

`依分級免測` 與 `UI QA 不適用` 都不屬於五種案例結果，也都不是 PASS。沒有適用案例就不造矩陣；報告仍保留適用性依據、其他驗證的證據入口與未確認項目。案例、發現與截圖等不適用欄位及自檢項目記不適用及理由，不為完成範本或抽查數量而編造。混合範圍只排除確定不適用的段落，剩餘 UI 仍依矩陣決定整體狀態。

🔴 **`尚未實跑` 的報告仍然有價值**（階段 1 的發現全都在），但整份不能出現任何讓人以為「測過、沒問題」的字眼。

狀態後面一定要接一句限定詞，說清楚這個判斷站在什麼證據上，例如：

> `部分執行`：12 條案例中執行 8 條，4 條因為無法重建全新環境而未執行；本輪只涵蓋網頁介面，未涵蓋行動裝置。

### 報告裡的每個數字都要能在矩陣上數出來

跑了幾條、過了幾條、找到幾個缺陷，寫之前先在矩陣上數一次。數不出來的數字就不要寫。

這條規則擋掉的是一種很自然的寫法：挖了很多、環境也架好了，結論就順手寫成「本輪共 30 條案例，未發現重大問題」。但矩陣上可能只有 8 格真的跑過。

## 🔴 出口標準與交回原流程

不准寫「覆蓋率需大於九成」「缺陷修復率需大於九成五」這類數字，除非那是這個專案已經訂好、而且指得出出處的門檻。

先區分「報告可以交付」與「QA 可以通過」。報告可如實帶著缺陷或缺口交付；其可觀察條件為：

- 範圍內每條案例都有終局狀態，沒有懸空的
- 每條 `FAIL` 和 `UNCLEAR` 都有對應的缺陷條目與證據
- 每條 `BLOCKED` 都有阻塞來源、未驗到的目標與補跑方式
- 每條 `NOT RUN` 都有原因，而且原因是可以處理的
- 所有 `UND` 類發現都已經丟回去問過，有答案或有明確的待決標記

無人值守遇到未決 `UND`，承接已有決策；必要的新決策交回原流程的 stop-and-ask，其餘標明待決，不臆造答案或另發訊息。

**原流程的完成判定：** 有既定 QA 出口就引用其來源；沒有時，範圍內必要案例須有證據且全為 `PASS`，沒有影響結論的未決預期／`UND` 或必要證據缺口，才能回報 QA 通過。`BLOCKED`、`NOT RUN`、未解決缺陷或預期未定都不能靠「已出報告」跨過。經人明確接受的例外須附來源，保留原五態並回報風險接受，不改寫為 PASS／無缺陷。只有已查證的 `UI QA 不適用` 可回到原流程，由其 AC／適用驗證證據決定任務是否完成，不宣稱 UI 實測通過。

**各級的出口**（沒有既定出口時；用在合併前，「通過」就是可以合併）：

| 級別 | 通過的條件 | 不能寫成什麼 |
|---|---|---|
| 免測級 | 不做 QA 判定，回到原流程 | 不寫通過 |
| 回歸級 | 這次修的題全 `PASS`，回歸腳本沒有變差（會晃的照平均判）。原本就錯而這次持平的不擋，但要列數字。repo 沒有回歸腳本時只看修的題，限定詞寫明「沒有回歸腳本，未驗其他題是否退步」 | 不寫畫面實測通過；只跑一次的會晃題組不算「沒有退步」 |
| 畫面級 | 改到的畫面與流程的案例全 `PASS`，沒有影響結論的未決預期 | 範圍外的畫面沒測，不寫成整個系統通過 |
| 完整級 | 照上一段 | 照上一段 |

多支 PR 一起驗時，逐支給結論。合在一起部署後出現退步，又分不出是哪一支造成的，可能相關的那幾支都先記未通過，並寫明「歸屬未確認」。

## 報告結構

環境紀錄另列 runner（Codex／Claude）、driver（Playwright／Codex computer-use）、目標 App／URL 與版本。Web 與桌面混合時分段標示；證據邊界列各通道「已取得／未取得／不適用」與原因，不把桌面缺少 network／console 說成已檢查。缺必要證據的案例不因換 driver 就改成 PASS。

```markdown
# QA 報告：<對象> <輪次>

## 一、摘要
分級與理由（完整級：新功能、使用者明講要完整驗收，或要對整個產品做 QA）
整體狀態 ＋ 證據限定詞
QA 出口判定（合併前用時，就是能不能合併；擋住的是哪幾條）
本輪範圍（涵蓋什麼、不涵蓋什麼）
本輪上限與實際用量（案例數；有呼叫模型的系統另寫問了幾題）
最需要注意的三件事

## 二、環境與可重現性
環境、執行時間、使用帳號
階段 0 的三樣交付物：三方版本座標、材料清單、前提盤點
前提重建方式（重建得出來的部分）

## 三、測試矩陣
案例 × 前提組合，五態標記
空白格與 NOT RUN 的說明

## 四、發現
4.0 本輪修正（多輪時）
4.1 沒有人決定過的（UND）  ← 放最前面
4.2 缺陷與阻塞（FAIL／UNCLEAR／BLOCKED，阻塞連回來源）
4.3 漏與錯位（GAP、MIS）
4.4 邊界與前提（EC）

## 五、分歧
（永遠要有這一節，沒有衝突就明寫「無」）

## 六、證據邊界
已驗證的：
未驗證的：
無法驗證的，以及缺什麼：

## 七、本輪寫入動作
（唯讀就明寫「本輪未寫入任何資料」）

## 八、待答問題與下一步
誰要回答、要什麼證據才關得掉

## 附錄：對帳表（多輪或多視角時）
```

通過的案例在矩陣裡一格帶過，不另寫段落；正文只展開失敗、`UNCLEAR`、`BLOCKED` 與退步。

### 精簡格式（回歸級、畫面級）

讀的人多半只想知道能不能合併，所以摘要放最前面，越短越好，細節只給出問題的地方。骨架在 `templates/qa-report-lite.md`。

```markdown
# QA 報告：<對象> <輪次>（<分級>）

## 一、摘要
分級與理由（一句話加依據）
QA 出口判定（能不能合併；多支 PR 時逐支一行）
整體狀態 ＋ 證據限定詞（寫出沒涵蓋的部分，例如「依分級未開瀏覽器」）
本輪上限與實際用量

## 二、版本與環境
待驗的提交與部署中的版本是否一致；環境與帳號
回歸腳本與基準的出處（回歸級）

## 三、結果
回歸腳本：變好、變差、持平各幾題；會晃的寫跑了幾次，平均多少
這次修的題，或改到的畫面與流程的案例：一條一行，通過的一行帶過

## 四、失敗與退步
每條照「缺陷條目怎麼寫」展開；沒有就寫「無」

## 五、分歧、證據邊界與寫入動作
各一兩行；沒有分歧寫「無」，唯讀寫「本輪未寫入任何資料」

## 六、待答問題與建議
超過上限想加的案例、分級待確認的部分、repo 該補的回歸腳本
```

### `UND` 為什麼放最前面

那是「沒有人決定過、但系統現在就這樣做」的清單，通常比缺陷更值錢也更容易被忽略。缺陷大家都知道要修，`UND` 不特別點出來就會默默變成既成事實，再過一陣子就變成「本來就是這樣設計的」。

## 缺陷條目怎麼寫

讀缺陷的人要做兩個判斷：這是不是真的問題、要不要先修。每一條依序回答四件事，讓他兩個都判斷得出來：

1. **是什麼、多嚴重**：一句話講哪裡壞、怎麼壞，接著 P0 到 P3。等級的理由要講到誰會碰到、多常碰到、碰到了繞不繞得過去
2. **從哪條線追來的**：`TC-##`，以及它指回的 `EC`／`UND`／`GAP`／`MIS`。回歸級寫回歸腳本的題號，或這次工單的哪一條
3. **怎麼再看到一次**：哪個環境、哪個角色、什麼前提，一步一步怎麼做。試了幾次、出現幾次，只試過一次就照實寫
4. **看到什麼、該看到什麼**：先寫實際看到的，**緊接著內嵌截圖**（見下）與適用 driver 的證據（Web network／console；桌面 UI 狀態／結果讀回／可用 log；回歸級沒有畫面，改附題目、實際輸出摘錄與結果檔的相對路徑）；再寫預期，標明 `依需求` 或 `推定`，推定要附依據。判斷不了的地方直接寫出來，不要留白

### 🔴 截圖要內嵌進報告，不是只在證據欄提一句

報告的讀者是要拿它**判斷哪幾條是真的缺陷**的人。一句「畫面顯示成功」說服不了人，一張圖可以。

- **有開 UI 的級別，每一條 `FAIL` 與 `UNCLEAR` 至少要有一張圖**，用 Markdown 圖片語法直接嵌在該條目裡，放在「實際結果」之後。回歸級不開 UI，證據改成輸出摘錄與結果檔。
- 通過的案例不放圖。畫面級另外每個改到的畫面放一張改後的樣子，證明改動真的上去了。
- **每張圖下面一行字，寫它證明了什麼**。單獨一張圖不構成證據。
- 沒有圖的條目，要在「證據邊界」那節寫明**為什麼沒有**（工具壞了／該現象拍不出來／當下沒截到），不要靜靜留白。
- 圖檔與報告**放在一起、用相對路徑**（例如報告旁的 `img/`），這樣整份可以直接轉 PDF 交出去，不必再修路徑。

```markdown
**實際結果**：送出後畫面顯示成功，但回到清單查不到這一筆。

![送出後顯示成功](img/TC-07-03-送出後顯示成功.png)
送出當下的畫面，標題寫著已建立。

![清單裡查不到](img/TC-07-04-清單查無.png)
同一時間的清單，該筆查無——兩張圖並列即為矛盾證據。
```

⚠️ **兩張圖並列的對照最有說服力**：「畫面說的」與「實際狀態」各一張，讀的人不必信你的描述。

🔴 **不准寫根因，除非真的查證過。** 看到現象就推根因是本 skill 明文禁止的事，那是 `diagnose` 的工作。寫「疑似與某某有關，未查證」可以，寫「根因是某某」不行。

## 十條出貨前自檢

逐條檢查並修正，全過才出貨。

1. **有開 UI 的級別，每一條 `FAIL` 與 `UNCLEAR` 是不是都嵌了圖、而且每張圖底下有一行說明它證明了什麼？** 沒有圖的，是不是在「證據邊界」寫明了原因？圖片路徑是不是相對路徑、從報告所在位置解析得到（整份要能直接轉 PDF）？回歸級的失敗與退步是不是附了輸出摘錄與結果檔路徑？
2. 每條發現是不是都指得出真實的來源（檔案行號、文件段落、實測紀錄）？
3. 隨便挑一條案例，順著它的 `Trace` 找得到是哪條發現長出來的嗎？（回歸級：找得到是哪條工單或哪一題回歸題嗎？）
4. 每個預期結果是不是標明了 `依需求`、`推定` 或 `預期未定`？**有沒有哪一條是從現況抄來的？** 發現與案例的存檔時間是不是早於第一次實跑（UI 操作或回歸腳本）？跑後改過的預期是不是保留了原文與理由？
5. 五種案例狀態是不是都用對了？`BLOCKED` 是否有阻塞來源且沒有被算成通過？`UI QA 不適用` 是否有查核依據，而非工具缺失或空矩陣？
6. 整體狀態是不是照適用性與矩陣決定的、後面有沒有限定詞？出口是否符合本節，沒有把報告交付、風險接受或未跑滿寫成 QA 全通過？
7. 第五節如果沒有內容，是不是寫了「無」，而不是把標題刪掉？
8. 挑三條發現，回頭找它的出處，找得到嗎？報告裡有沒有哪句話是寫的時候「覺得應該是這樣」、材料裡其實沒有的？這種句子不屬於報告正文，移到待答問題那一節，並註明是誰、憑什麼這樣猜。
9. 寫入動作那一節在不在？唯讀的話有沒有明寫「本輪未寫入任何資料」？
10. 報告開頭有沒有寫分級與理由、本輪上限與實際用量？有沒有超過上限卻沒先問？會晃的題組是不是跑了兩次以上才判退步？多支 PR 一起驗時，是不是逐支給了結論？

## 兩個常見錯誤

- ❌ 算通過率時把 `NOT RUN` 或空白格也放進分母，讓比例看起來比實際高
- ❌ 寫報告時才處理「兩輪說法不一樣」「有人要求先當作通過」這類事情。這些在對帳時就該處理完（見 `merge-rules.md`），報告只照對帳結果寫
