# qa — 把「測都綠但一用就炸」查清楚並出報告

## 這隻 skill 解的問題

元件各自測都過，接起來從介面走就卡關。根因通常不是程式寫錯，是**系統心裡有規矩、但沒說出口**：

- 某張表預設是空的，沒人建過資料就整條路被擋
- 某個動作只做得了一次，第二次被無聲擋掉
- 某支端點回成功，但事情其實沒成
- 某條路實際要管理員權限，跟當初講的「使用者自助完成」對不起來

這些規矩既不在需求文件裡、也不在使用者看得到的地方，只躺在程式的判斷式裡。單元測試與端點測試永遠綠，因為兩邊各自都自洽。

**本 skill 把那些規矩挖出來、逐條驗一次、寫成報告。**

## 不做的事

| 不做 | 去哪 |
|---|---|
| 寫使用者手冊或管理者手冊 | `project-docs`（本 skill 只交素材） |
| 找已知缺陷的根因 | `diagnose` |
| 效能、壓測、資安滲透 | 不在範疇 |
| 修程式 | 不在範疇，本 skill 唯讀 |
| 事後歸因（把新炸的前提收回清單） | 尚未實作 |

## 適用 UI 時的五個階段，順序不可調換

```
0 範圍與輸入稽核
      ↓
1 挖（唯讀，不碰執行環境）
      ↓
2 轉成測試案例
      ↓
3 跑（有環境才跑）
      ↓
4 報告
```

🔴 **一定要先挖完才准跑。** 反過來做的話，注意力會被畫面上看到的東西綁住，只挖得出這次剛好踩到的幾個，潛伏的一個都挖不到。那等於把人工亂點換成機器亂點，沒有解決任何問題。

## 階段 0：範圍與輸入稽核

先確認這輪要測哪些畫面／App 與角色，**也講清楚不測哪些**：沒寫出來的，讀報告的人會以為測過了。使用者或無人值守 dispatch 已定的範圍與授權直接承接，不重新訪談；缺的部分如實列出。

**先讀 [UI 操作與證據來源](references/ui-driver.md)。** Web 優先 Playwright MCP；原生桌面與跨 App 流程走 Codex computer-use，此分支僅限實際具備工具的 Codex session。跨 UI QA 建議 Codex，但要驗工具可用性，不因 runner 名稱就假定能操作。記錄 driver／runner／目標與證據能力，缺少的段落不假裝測過。

依 ui-driver 確認本輪沒有適用的 UI 時，留下範圍與查核依據，直接進階段 4，依報告契約回報 `UI QA 不適用`；其餘流程維持階段 0–4 的順序。不把缺工具或缺環境當成不適用，也不替原流程的 CLI／背景服務驗證宣告通過。

QA 的需求依據是已核准 spec／PRD／其他需求原件，測試案例由本 skill 在階段 2 產生，不要求先跑 project-docs。project-docs 只在需要補建技術文件或手冊時接入；它也可在 QA 後接成功路徑素材。ADR 只說明決策理由，不能取代需求與可驗證預期。

然後交出三樣東西，才進階段 1。三樣都會原封不動放進報告的「環境與可重現性」和「證據邊界」。

**一、版本座標**：見下方「三方版本對齊」。

**二、材料清單**：拿到的每一份材料一列。

| 材料 | 拿到了嗎 | 哪個版本 | 跟誰對不上 |
|---|---|---|---|
| 需求文件 | | | |
| UI／桌面端與服務端程式碼（依實際架構） | | | |
| schema 與種子資料 | | | |
| 既有測試與缺陷紀錄 | | | |
| 可用環境、目標 App／URL、各角色帳號與 UI driver | | | |

「跟誰對不上」這欄最容易空著。需求文件如果是跟 AI 討論出來的，常常自己前後不一致，或是改了一半沒回填。找到落差**不要預設哪一份對**，寫下兩邊各怎麼說，留給人判。

缺材料不是停工的理由。缺的那一列照樣列著，寫明它會讓哪一段挖不深，然後用手上有的繼續做。

**三、前提盤點**：見下方。

### 🔴 三方版本對齊

本 skill 的方法是「讀 repo 裡的程式碼、測跑著的那套系統」，所以**文件版本、原始碼版本、部署版本三者天生可能不一致**，而三者一歪，測出來的落差就分不清是缺陷還是版本差。

開跑前各記一個版本座標（提交、標籤、映像、建置時間都行），比對過再往下。**對不上就先寫進報告、並把受影響的範圍標出來**，不要讓它混進缺陷清單。

> 典型災情：需求文件描述了一整個功能，而部署端根本還沒有它。那一整章的發現全部作廢，而且要等跑到一半才發現。

### 🔴 前提盤點

把這輪要驗的前提逐條分成四類：**現成／可以造出來／造不出來／還沒確認但先當成立**。

第四類是為了能往下挖而先認定的事，例如「先當作一般使用者也能建立專案」。每一條旁邊寫它撐著哪幾條發現，之後被推翻時才知道要回頭改哪些。

這件事現在做，是為了讓階段 2 排序時知道哪些案例注定跑不到——否則會挖出一大批、到階段 3 才一條條撞牆。報告裡「沒測到」要能分辨是**沒去測**還是**測不到**，那個分界線就是在這裡畫的。

## 階段 1：挖（唯讀）

三種材料擺在一起對照，一種都不能少：

```
需求文件（含跟 agent 討論產生的）   ← 說了「該做什麼」
前端程式碼                          ← 使用者這一側實際要求什麼
後端程式碼                          ← 系統這一側實際擋什麼
初始資料與 schema                   ← 哪些東西預設是空的
```

### 1a. 三方對照，掉出三類發現

| 編號 | 類型 | 意思 | 危險度 |
|---|---|---|---|
| `GAP-##` | 漏 | 需求說了，實作沒做 | 中，通常自己會發現 |
| `UND-##` | **沒人決定過的** | **實作做了，需求沒說** | 🔴 **最高** |
| `MIS-##` | 錯位 | 兩邊都有，但做法不同 | 高 |

🔴 **`UND-##` 是本 skill 最核心的產出。** 那是實作時自己補上的假設，沒有任何人拍板過，但它現在就是系統行為。純讀程式碼挖不出來，因為讀程式碼只會覺得「這裡有個權限檢查，合理」；非得把需求文件擺旁邊，才看得出「從來沒有人說過要管理員」。

### 1b. 沿八個面向挖隱含要求，編號 `EC-##`

資料從哪裡來、填進去的值、時間與先後、狀態、誰在操作、系統外部、**畫面上的字**、疊在一起。每個面向要問什麼見 `references/finding-contract.md`。

每個面向挑兩三條最可能出事的就夠了。挖出一百條平均用力的邊界，等於沒挖。

#### 🔴 「畫面上的字」為什麼要獨立一個面向

其他面向問的都是「機器這樣餵會怎樣」。但**介面上的字本身就會壞，而且壞法自成一類**——單元測試與端點測試永遠看不到它，因為那些字不參與任何判斷式。這正是本 skill 的守備範圍。

三個子問，逐頁掃：

| 問 | 典型壞法 |
|---|---|
| 畫面提到的東西**真的存在嗎** | 說明叫人「看底下標記 X 的那幾個」，而系統從來不產生 X；提示叫人去某頁做某事，那頁沒有那個功能 |
| 用的是**使用者的領域語言嗎** | 欄位名與選項沿用開發時某個特定客戶的行業術語，換一個行業的人填不出來、也不知道填了會怎樣 |
| **限制與必填說得出來嗎** | 按鈕是灰的但不說少了什麼；擋下來了但訊息講錯對象；同一個東西在三個頁面有三種叫法 |

⚠️ **這一格要看使用者實際讀到的內容，不是只比對狀態碼。** Web 用無障礙樹取文字；桌面依 ui-driver 用可讀 UI／AX 或明列限制的視覺證據。問的是「一個第一次來的人看得懂嗎」。

### 1c. 每條發現回答七欄

七欄與證據狀態的定義見 `references/finding-contract.md`。答不出來的欄位要補，不要帶著空欄進報告。

### 1d. 這個階段只動筆

階段 1 只讀程式、只寫發現，不改檔案，也不碰執行中的系統。

挖到「這條路要管理員」時，**寫成一條待判定的 `UND` 丟回給人**，不要自己宣判它是錯的。程式碼只看得到做了什麼，看不到本來想做什麼。同樣地，數值或規則找不到出處就寫「不明」；程式有做、需求沒寫的，在「需求怎麼說」那欄寫「需求未提及」。兩者都不要替它補一個聽起來合理的理由。

## 階段 2：轉成測試案例

每條發現轉成一條或多條 `TC-##`。

### 每條案例都指回一條發現

每條 `TC-##` 標出它從哪條 `EC`／`GAP`／`UND`／`MIS` 長出來。這條線斷了，報告裡的 FAIL 就回答不了「所以是哪個規矩出了問題」。

需求文件多半沒有編號，這正是階段 1 要先編發現號的原因：發現編號就是案例的錨點。只寫「參考需求文件」等於沒寫。

### 🔴 預期結果只能從需求意圖推，不准從現況抄

這是整隻 skill 最容易壞掉的地方。

如果讓程式碼決定預期結果，會寫出「使用者走這條路，預期得到 403」，因為程式就是這樣做的。**那測試永遠會過，整份報告是廢的。**

正確做法：

| 情況 | 預期結果怎麼寫 |
|---|---|
| 需求明確講過 | 照需求寫，標 `依需求` |
| 需求沒講，但產品意圖推得出來 | 照意圖寫，標 `推定` |
| 兩者都沒有 | **不要編**。標 `預期未定`，列成待答問題 |

`推定` 的預期跟現況不一致時，**那就是一條 FAIL**，不是把預期改成現況。

### 🔴 要有一類案例是「刻意不照文件的順序做」

需求文件（尤其是操作手冊）會把前置條件與建議步驟寫清楚。照著走，那些前置擋住的缺陷**就不會發生**——對使用者是好事，對測試是盲區。

**文件寫得越好，這個盲區越大。** 而真實使用者不照順序：他跳過設定、先做第三步、少做一步就開始用。那些路徑沒有任何文件描述過，也就沒有任何人走過。

所以每一組有前置的流程，至少要有一條案例是**故意把前置拿掉或調換順序**，問三件事：

1. 系統擋不擋得住
2. 擋住的時候，使用者知不知道自己少做了什麼
3. 沒擋住的話，壞掉的東西**事後看得出來嗎**（最危險的是看起來成功、其實少了一半）

預期結果照「依需求／推定／預期未定」那條規則寫，不要因為「文件沒說不能這樣做」就跳過。

### 什麼算同一條

兩條發現可能長出幾乎一樣的案例。判斷方法：**讓兩個人各照一條去跑，他們的操作和看到的結果會一樣嗎？** 一樣就併成一條，Trace 兩條發現都留；只要操作或判定方式不一樣，就分開寫。

拿不準的時候留兩條，並開一條待答問題。案例多一條只是多跑幾分鐘，併錯了會讓一個問題沒人測。

### 案例裡的數字要有出處

案例會寫到具體的值：上限、逾時秒數、錯誤碼、網址路徑。這些只能抄自材料。材料沒寫的，案例裡寫「依實際上限」之類的描述，並在階段 0 的材料清單補一筆缺什麼。

## 階段 3：跑

沒有可用環境時**跳過本階段**，所有案例標 `NOT RUN`，直接進階段 4。報告照出，只是證據等級低。

執行紀律、五種結果狀態、截圖規則、不准改動目標系統的界線，全部在 `references/run-discipline.md`。**跑之前整份讀完，並核對階段 0 已選的 ui-driver 與證據通道。**

摘要三條：

1. **預設唯讀。** 要寫入資料之前，先確認這個環境是可拋棄的，並且把每一個寫入動作記下來
2. **結果分五態**，不是兩態：`PASS`／`FAIL`／`UNCLEAR`／`BLOCKED`／`NOT RUN`。**`UNCLEAR` 是擋對了但使用者無從得知為什麼** —— 卡關的主因通常在這格，二元分類會讓它整個消失
3. **截圖當下就分類**：`defect` 是缺陷證據，`manual` 是之後給手冊用的成功路徑素材。同一趟走完全程，兩種一起採

## 階段 4：報告

格式、整體狀態與交回原流程的出口判準在 `references/report-contract.md`，出貨前跑完那份的九條自檢。無人值守也依同一判準回報，不以產出報告代替 QA 通過。

先記住一件事：**有適用 UI 時，報告的結論是從矩陣算出來的，不是從印象寫出來的。** 實際跑過、有證據的格子才能撐起結論；`NOT RUN` 不能寫成「沒問題」，`BLOCKED` 不代表目標已驗過。空矩陣是 `尚未實跑`；只有階段 0 已查證無 UI 才能記 `UI QA 不適用`，不能由空矩陣倒推不適用。

## 多輪或多視角結果的合併

同一個對象跑過不只一輪，或是讓 AI 換幾個視角各挖一遍之後，結果要合併成一份。

做法在 `references/merge-rules.md`：把每一份結果當成一本帳，排成對帳表逐列比，每一列都要有去處（已修好、延續、本輪新增、補跑、說法衝突、看不出是不是同一列）。

一條先講：**決定帶著問題上線是人的權力，但那是一筆「風險接受」紀錄，不是把 `FAIL` 改成 `PASS`。**
