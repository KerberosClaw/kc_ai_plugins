# qa — 把「測都綠但一用就炸」查清楚並出報告

## 這隻 skill 解的問題

元件各自測都過，接起來從介面走就卡關。根因通常不是程式寫錯，是**系統心裡有規矩、但沒說出口**：

- 某張表預設是空的，沒人建過資料就整條路被擋
- 某個動作只做得了一次，第二次被無聲擋掉
- 某支端點回成功，但事情其實沒成
- 某條路實際要管理員權限，跟當初講的「使用者自助完成」對不起來

這些規矩既不在需求文件裡、也不在使用者看得到的地方，只躺在程式的判斷式裡。單元測試與端點測試永遠綠，因為兩邊各自都自洽。

**本 skill 把那些規矩挖出來、逐條驗一次、寫成報告。**

但不是每次改動都需要挖一整輪。開跑前先分級（見「先分級」一節），分到完整級（新功能、明講要完整驗收，或沒有特定改動而要對整個產品做 QA）才走這一整套。

## 不做的事

| 不做 | 去哪 |
|---|---|
| 寫使用者手冊或管理者手冊 | `project-docs`（本 skill 只交素材） |
| 找已知缺陷的根因 | `diagnose` |
| 效能、壓測、資安滲透 | 不在範疇 |
| 修程式 | 不在範疇，本 skill 唯讀 |
| 事後歸因（把新炸的前提收回清單） | 尚未實作 |

## 先分級：所有階段之前的第一件事

只改後端判斷而畫面沒變的改動，開瀏覽器從頭挖一輪，子代理一輪動輒幾十萬 token；同樣的退步，repo 現成的回歸腳本在測試主機上跑一次就抓得到，幾乎不花 token。所以**先看這次改了什麼，再決定驗多深**，並在報告開頭寫明分了哪一級、為什麼。

### 四個級別

| 級別 | 改動類型 | 驗多深 |
|---|---|---|
| 免測級 | 只改文件 | 不實測，報告一句話說明 |
| 回歸級 | 只改後端判斷，畫面與操作流程沒變 | 跑 repo 登記的回歸腳本，加上這次修的那幾題實際跑一次；**不開瀏覽器** |
| 畫面級 | 改到畫面或使用者操作流程 | 瀏覽器實測，**只測改到的畫面與流程** |
| 完整級 | 新功能，或使用者明講要完整驗收 | 原本的完整流程：階段 0 到 4，挖沒說出口的規矩，案例排完整 |

桌面 App 的「瀏覽器」換成 ui-driver 選的操作方式，分級的判法不變。

### 怎麼判

看這次改動的 diff 或改動清單（PR、提交範圍、工單列的檔案），對照：

| 看到的改動 | 歸到 |
|---|---|
| 只有說明文件或註解（會被程式讀進去或顯示在畫面上的不算，例如寫成 Markdown 的提示詞模板、畫面會載入的說明頁） | 免測級 |
| 只有服務端的判斷、提示詞、檢索或資料處理；前端檔案沒動，API 回應的欄位、格式與錯誤訊息也沒變 | 回歸級 |
| 前端檔案、畫面上的字、路由或表單有變；API 回應的欄位、格式或錯誤訊息有變（畫面會顯示）；操作步驟有變 | 畫面級 |
| 新頁面、新流程、新角色；或使用者明講要完整驗收 | 完整級 |
| 沒有特定改動，要對整個產品或整條流程做一輪 QA | 完整級 |

- **預設取涵蓋得了這次改動的最小一級。** 同一支 PR 有後端也有畫面改動，就是畫面級；後端那部分照下方跑回歸腳本。
- **判斷不了就問使用者，不要自己升級。** 無人值守時照派工單寫的級別；派工單沒寫又判斷不了，先取較小的一級跑完，報告開頭標「分級待確認」，寫出較大那一級還有哪些沒驗，交回原流程決定。
- 跑到一半發現分錯（例如回歸級的改動其實讓畫面顯示變了），停下來說明，等人決定換不換級，不自己改。
- 報告開頭的分級寫一句話加依據，例如「回歸級：diff 只動服務端三個檔，API 回應格式沒變」。

⚠️ 回歸級不開瀏覽器，是因為**這次改動**沒碰到畫面，不是產品沒有畫面。所以不能記 `UI QA 不適用`（那只給產品在核准範圍內本來就沒有 UI 的情況），也不能寫成畫面實測通過。

### 各級走哪幾段

| 級別 | 階段 0 範圍與輸入 | 階段 1 挖 | 階段 2 案例 | 階段 3 跑 | 階段 4 報告 |
|---|---|---|---|---|---|
| 免測級 | 列出改動清單 | 不做 | 不做 | 不做 | 一句話 |
| 回歸級 | 版本座標；找回歸腳本與上一次的基準 | 不做 | 只寫這次修的題（不是修正的改動，就寫它直接影響的題）與預期行為 | 回歸腳本加修的題，不開 UI | 精簡格式 |
| 畫面級 | 版本座標；選 ui-driver；範圍只圈改到的畫面與流程 | 只對改到的畫面做「畫面上的字」三問（見 1b），並挖改到的流程的前置與順序 | 每個改到的畫面或流程一條成功路徑；有前置的再加一條不照順序的 | 只跑這些案例 | 精簡格式 |
| 完整級 | 全套 | 全套 | 全套 | 全套 | 完整格式 |

不論哪一級都要守的兩條：

- **版本要對。** 有實跑的級別，開跑前都要確認部署中的版本就是這次要驗的提交（三方版本對齊的最小版）。對不上就先停，不然驗到的是別的東西。
- **預期先寫再跑。** 回歸級與畫面級的預期一樣從需求或這次的工單推，不從現況抄；跑之前寫進報告旁的檔案並記時間（規則同階段 2 最後一節）。

### 優先用 repo 現成的回歸腳本

回歸級一定要找；畫面級與完整級有動到後端時也照跑，反正幾乎不花 token。

1. **先找。** 依序看 `owl.md`（真人問法題組、真人操作題組，或另外登記的回歸腳本）、`AGENTS.md`／`CLAUDE.md`、`README`，再看測試目錄（例如 `tests/`、`eval/`、`scripts/`）。
2. **有就照登記的方式直接跑**：在哪台主機、用什麼指令，照寫的做。只在目錄裡找到、文件沒寫用法的，先讀腳本，確認它不寫正式資料，也看清參數怎麼給；看不出來就問，不猜參數硬跑。
3. **報告只寫跟上一次的差異**：變好、變差、持平各幾題。基準取同一個環境上一次的結果（腳本自己的結果檔，或上一份報告）。有變差才逐題細查，持平的不展開。比法就是 `references/merge-rules.md` 的對帳：變好對應「已修好」，變差對應「本輪新增」裡的退步，原本就錯而這次持平的照「延續」只列數字。
4. **沒有基準**：環境允許的話，部署前先對現行版本跑一次當基準；做不到就照實寫「沒有基準」，這次的結果留給下一次比，不用它判退步。
5. **repo 沒有回歸腳本**：照分級的方式做。回歸級就只跑這次修的題，用 API 或指令直接問，不開瀏覽器；報告的建議寫「建議 repo 補一支回歸腳本，並登記在 `owl.md` 或 `AGENTS.md`」。

### 會晃的題組，跑兩次以上才判

有些題組每次跑都會差幾題，呼叫模型的系統最常見。登記處寫了會晃，或同一個版本跑兩次結果不同，就當會晃的題組處理：

- 至少跑兩次取平均，再跟基準的平均比。
- 差距落在已知的晃動範圍內，記持平。
- 不用單次結果下「退步」的結論。只跑了一次的，報告寫「單次結果，未判定」。

### 每輪先講上限

開跑前在報告檔寫明這輪的上限，碰到上限就停下來問，不自己擴大範圍。

| 上限 | 怎麼訂 |
|---|---|
| 最多幾條案例 | 從改動推，不憑感覺：回歸級是這次修的題數；畫面級是改到的畫面與流程各一條成功路徑，有前置的再加一條不照順序；完整級是階段 2 排出來的數量 |
| 最多問模型幾題（有呼叫模型的系統） | 回歸腳本的題數乘上要跑的次數（會晃的至少兩次），加上修的題各一次 |

上限寫成具體數字，報告摘要再寫實際用了多少。跑的過程想加案例（例如看到可疑的地方），先記下來，問過才加；無人值守時不加，寫進待答問題當下一輪的建議。

### 多支 PR 一次驗

同一批要合併的 PR，合在一起部署，驗一次就好，不要一支驗一輪：

- 每支 PR 各自分級，這一輪的範圍是各支的聯集；回歸腳本只跑一輪（會晃的照上面跑兩次以上）。
- 報告逐支列結論：哪一級、驗了什麼、能不能合併。
- 合在一起部署後出現退步，單憑這一輪分不出是哪一支造成的。照實寫可能相關的是哪幾支；要拆開分別部署細查，先問。

## 完整級的五個階段，順序不可調換

```
0 範圍與輸入稽核
      ↓
1 挖（唯讀，不碰執行環境）
      ↓
2 轉成測試案例
      ↓
3 跑（有環境才跑）
      ↓
4 報告
```

畫面級照「各級走哪幾段」只走其中一部分，順序一樣不能調換；回歸級與免測級不走這五段，只借用版本座標、執行紀律與報告契約。

🔴 **一定要先挖完才准跑。** 反過來做的話，注意力會被畫面上看到的東西綁住，只挖得出這次剛好踩到的幾個，潛伏的一個都挖不到。那等於把人工亂點換成機器亂點，沒有解決任何問題。

## 階段 0：範圍與輸入稽核

先確認這輪要測哪些畫面／App 與角色，**也講清楚不測哪些**：沒寫出來的，讀報告的人會以為測過了。使用者或無人值守 dispatch 已定的範圍與授權直接承接，不重新訪談；缺的部分如實列出。

**先讀 [UI 操作與證據來源](references/ui-driver.md)。** Web 優先 Playwright MCP；原生桌面與跨 App 流程走 Codex computer-use，此分支僅限實際具備工具的 Codex session。跨 UI QA 建議 Codex，但要驗工具可用性，不因 runner 名稱就假定能操作。記錄 driver／runner／目標與證據能力，缺少的段落不假裝測過。

依 ui-driver 確認本輪沒有適用的 UI 時，留下範圍與查核依據，直接進階段 4，依報告契約回報 `UI QA 不適用`；其餘流程維持階段 0–4 的順序。不把缺工具或缺環境當成不適用，也不替原流程的 CLI／背景服務驗證宣告通過。

QA 的需求依據是已核准 spec／PRD／其他需求原件，測試案例由本 skill 在階段 2 產生，不要求先跑 project-docs。project-docs 只在需要補建技術文件或手冊時接入；它也可在 QA 後接成功路徑素材。ADR 只說明決策理由，不能取代需求與可驗證預期。

然後交出三樣東西，才進階段 1。三樣都會原封不動放進報告的「環境與可重現性」和「證據邊界」。

**一、版本座標**：見下方「三方版本對齊」。

**二、材料清單**：拿到的每一份材料一列。

| 材料 | 拿到了嗎 | 哪個版本 | 跟誰對不上 |
|---|---|---|---|
| 需求文件 | | | |
| UI／桌面端與服務端程式碼（依實際架構） | | | |
| schema 與種子資料 | | | |
| 既有測試與缺陷紀錄 | | | |
| 可用環境、目標 App／URL、各角色帳號與 UI driver | | | |

「跟誰對不上」這欄最容易空著。需求文件如果是跟 AI 討論出來的，常常自己前後不一致，或是改了一半沒回填。找到落差**不要預設哪一份對**，寫下兩邊各怎麼說，留給人判。

缺材料不是停工的理由。缺的那一列照樣列著，寫明它會讓哪一段挖不深，然後用手上有的繼續做。

**三、前提盤點**：見下方。

### 🔴 三方版本對齊

本 skill 的方法是「讀 repo 裡的程式碼、測跑著的那套系統」，所以**文件版本、原始碼版本、部署版本三者天生可能不一致**，而三者一歪，測出來的落差就分不清是缺陷還是版本差。

開跑前各記一個版本座標（提交、標籤、映像、建置時間都行），比對過再往下。**對不上就先寫進報告、並把受影響的範圍標出來**，不要讓它混進缺陷清單。

> 典型災情：需求文件描述了一整個功能，而部署端根本還沒有它。那一整章的發現全部作廢，而且要等跑到一半才發現。

### 🔴 前提盤點

把這輪要驗的前提逐條分成四類：**現成／可以造出來／造不出來／還沒確認但先當成立**。

第四類是為了能往下挖而先認定的事，例如「先當作一般使用者也能建立專案」。每一條旁邊寫它撐著哪幾條發現，之後被推翻時才知道要回頭改哪些。

這件事現在做，是為了讓階段 2 排序時知道哪些案例注定跑不到——否則會挖出一大批、到階段 3 才一條條撞牆。報告裡「沒測到」要能分辨是**沒去測**還是**測不到**，那個分界線就是在這裡畫的。

## 階段 1：挖（唯讀）

三種材料擺在一起對照，一種都不能少：

```
需求文件（含跟 agent 討論產生的）   ← 說了「該做什麼」
前端程式碼                          ← 使用者這一側實際要求什麼
後端程式碼                          ← 系統這一側實際擋什麼
初始資料與 schema                   ← 哪些東西預設是空的
```

### 1a. 三方對照，掉出三類發現

| 編號 | 類型 | 意思 | 危險度 |
|---|---|---|---|
| `GAP-##` | 漏 | 需求說了，實作沒做 | 中，通常自己會發現 |
| `UND-##` | **沒人決定過的** | **實作做了，需求沒說** | 🔴 **最高** |
| `MIS-##` | 錯位 | 兩邊都有，但做法不同 | 高 |

🔴 **`UND-##` 是本 skill 最核心的產出。** 那是實作時自己補上的假設，沒有任何人拍板過，但它現在就是系統行為。純讀程式碼挖不出來，因為讀程式碼只會覺得「這裡有個權限檢查，合理」；非得把需求文件擺旁邊，才看得出「從來沒有人說過要管理員」。

### 1b. 沿八個面向挖隱含要求，編號 `EC-##`

資料從哪裡來、填進去的值、時間與先後、狀態、誰在操作、系統外部、**畫面上的字**、疊在一起。每個面向要問什麼見 `references/finding-contract.md`。

每個面向挑兩三條最可能出事的就夠了。挖出一百條平均用力的邊界，等於沒挖。

#### 🔴 「畫面上的字」為什麼要獨立一個面向

其他面向問的都是「機器這樣餵會怎樣」。但**介面上的字本身就會壞，而且壞法自成一類**——單元測試與端點測試永遠看不到它，因為那些字不參與任何判斷式。這正是本 skill 的守備範圍。

三個子問，逐頁掃：

| 問 | 典型壞法 |
|---|---|
| 畫面提到的東西**真的存在嗎** | 說明叫人「看底下標記 X 的那幾個」，而系統從來不產生 X；提示叫人去某頁做某事，那頁沒有那個功能 |
| 用的是**使用者的領域語言嗎** | 欄位名與選項沿用開發時某個特定客戶的行業術語，換一個行業的人填不出來、也不知道填了會怎樣 |
| **限制與必填說得出來嗎** | 按鈕是灰的但不說少了什麼；擋下來了但訊息講錯對象；同一個東西在三個頁面有三種叫法 |

⚠️ **這一格要看使用者實際讀到的內容，不是只比對狀態碼。** Web 用無障礙樹取文字；桌面依 ui-driver 用可讀 UI／AX 或明列限制的視覺證據。問的是「一個第一次來的人看得懂嗎」。

### 1c. 每條發現回答七欄

七欄與證據狀態的定義見 `references/finding-contract.md`。答不出來的欄位要補，不要帶著空欄進報告。

### 1d. 這個階段只動筆

階段 1 只讀程式、只寫發現，不改檔案，也不碰執行中的系統。

挖到「這條路要管理員」時，**寫成一條待判定的 `UND` 丟回給人**，不要自己宣判它是錯的。程式碼只看得到做了什麼，看不到本來想做什麼。同樣地，數值或規則找不到出處就寫「不明」；程式有做、需求沒寫的，在「需求怎麼說」那欄寫「需求未提及」。兩者都不要替它補一個聽起來合理的理由。

## 階段 2：轉成測試案例

每條發現轉成一條或多條 `TC-##`。

### 每條案例都指回一條發現

每條 `TC-##` 標出它從哪條 `EC`／`GAP`／`UND`／`MIS` 長出來。這條線斷了，報告裡的 FAIL 就回答不了「所以是哪個規矩出了問題」。

需求文件多半沒有編號，這正是階段 1 要先編發現號的原因：發現編號就是案例的錨點。只寫「參考需求文件」等於沒寫。

### 🔴 預期結果只能從需求意圖推，不准從現況抄

這是整隻 skill 最容易壞掉的地方。

如果讓程式碼決定預期結果，會寫出「使用者走這條路，預期得到 403」，因為程式就是這樣做的。**那測試永遠會過，整份報告是廢的。**

正確做法：

| 情況 | 預期結果怎麼寫 |
|---|---|
| 需求明確講過 | 照需求寫，標 `依需求` |
| 需求沒講，但產品意圖推得出來 | 照意圖寫，標 `推定` |
| 兩者都沒有 | **不要編**。標 `預期未定`，列成待答問題 |

`推定` 的預期跟現況不一致時，**那就是一條 FAIL**，不是把預期改成現況。

### 🔴 要有一類案例是「刻意不照文件的順序做」

需求文件（尤其是操作手冊）會把前置條件與建議步驟寫清楚。照著走，那些前置擋住的缺陷**就不會發生**——對使用者是好事，對測試是盲區。

**文件寫得越好，這個盲區越大。** 而真實使用者不照順序：他跳過設定、先做第三步、少做一步就開始用。那些路徑沒有任何文件描述過，也就沒有任何人走過。

所以每一組有前置的流程，至少要有一條案例是**故意把前置拿掉或調換順序**，問三件事：

1. 系統擋不擋得住
2. 擋住的時候，使用者知不知道自己少做了什麼
3. 沒擋住的話，壞掉的東西**事後看得出來嗎**（最危險的是看起來成功、其實少了一半）

預期結果照「依需求／推定／預期未定」那條規則寫，不要因為「文件沒說不能這樣做」就跳過。

### 什麼算同一條

兩條發現可能長出幾乎一樣的案例。判斷方法：**讓兩個人各照一條去跑，他們的操作和看到的結果會一樣嗎？** 一樣就併成一條，Trace 兩條發現都留；只要操作或判定方式不一樣，就分開寫。

拿不準的時候留兩條，並開一條待答問題。案例多一條只是多跑幾分鐘，併錯了會讓一個問題沒人測。

### 案例裡的數字要有出處

案例會寫到具體的值：上限、逾時秒數、錯誤碼、網址路徑。這些只能抄自材料。材料沒寫的，案例裡寫「依實際上限」之類的描述，並在階段 0 的材料清單補一筆缺什麼。

### 🔴 開跑前先把發現與案例存檔

進階段 3 之前，把階段 1 的發現與本階段的案例（每條含 Trace、前提、預期結果與 `依需求`／`推定`／`預期未定` 標記）存成檔案放在報告旁邊，並在檔案開頭記下存檔時間；第一次 UI 操作（回歸級是第一次跑腳本）要在這之後。實跑只補實際結果與證據。跑到一半發現某條預期寫錯，保留原本的預期，旁邊註明改成什麼、為什麼，不直接覆寫。

只在腦中挖完就開跑，事後沒有人分得出預期是先推好的，還是看了畫面才補上的。「不准從現況抄」這條規則查不查得到，就靠這一步。

## 階段 3：跑

沒有可用環境時**跳過本階段**，所有案例標 `NOT RUN`，直接進階段 4。報告照出，只是證據等級低。

執行紀律、五種結果狀態、截圖規則、不准改動目標系統的界線，全部在 `references/run-discipline.md`。**跑之前整份讀完，並核對階段 0 已選的 ui-driver 與證據通道。**

摘要三條：

1. **預設唯讀。** 要寫入資料之前，先確認這個環境是可拋棄的，並且把每一個寫入動作記下來
2. **結果分五態**，不是兩態：`PASS`／`FAIL`／`UNCLEAR`／`BLOCKED`／`NOT RUN`。**`UNCLEAR` 是擋對了但使用者無從得知為什麼** —— 卡關的主因通常在這格，二元分類會讓它整個消失
3. **截圖當下就分類**：`defect` 是缺陷證據，`manual` 是之後給手冊用的成功路徑素材。完整級同一趟走完全程，兩種一起採；畫面級只截失敗的地方，加上每個改到的畫面一張；回歸級不截圖

## 階段 4：報告

格式、整體狀態與交回原流程的出口判準在 `references/report-contract.md`，出貨前跑完那份的十條自檢。無人值守也依同一判準回報，不以產出報告代替 QA 通過。

報告格式跟著分級走：免測級只寫一句話；回歸級與畫面級用精簡格式（`templates/qa-report-lite.md`）；完整級用完整格式（`templates/qa-report.md`）。不論哪一種，開頭一段摘要就要看得出分了哪一級、能不能合併；通過的案例一行帶過，只展開失敗、退步與使用者看不懂的地方。

先記住一件事：**有適用 UI 時，報告的結論是從矩陣算出來的，不是從印象寫出來的。** 實際跑過、有證據的格子才能撐起結論；`NOT RUN` 不能寫成「沒問題」，`BLOCKED` 不代表目標已驗過。空矩陣是 `尚未實跑`；只有階段 0 已查證無 UI 才能記 `UI QA 不適用`，不能由空矩陣倒推不適用。回歸級同樣只認跑過、有輸出的題目，結論從結果表算。

## 多輪或多視角結果的合併

同一個對象跑過不只一輪，或是讓 AI 換幾個視角各挖一遍之後，結果要合併成一份。

做法在 `references/merge-rules.md`：把每一份結果當成一本帳，排成對帳表逐列比，每一列都要有去處（已修好、延續、本輪新增、補跑、說法衝突、看不出是不是同一列）。

一條先講：**決定帶著問題上線是人的權力，但那是一筆「風險接受」紀錄，不是把 `FAIL` 改成 `PASS`。**
